# Supabase 분리배출 데이터 연결

## 실제 프로젝트에 적용

1. [SQL Editor](https://supabase.com/dashboard/project/phutcroispzgqqtrpgjn/sql/new)를 엽니다.
2. `supabase/setup.sql` 전체를 붙여넣고 Run을 누릅니다.
3. Success를 확인합니다. Table Editor에서 아래 6개 테이블이 생성되고 `disposal_items`에 25개 품목 묶음이 있어야 합니다.
4. 앱을 배포하고 새로고침한 뒤 로그인해 판별·기록·통계를 확인합니다.

프로젝트 URL과 Publishable key만으로는 테이블·함수·RLS를 만들 수 없습니다. 이 최초 설정은 프로젝트 소유자가 SQL Editor에서 실행해야 합니다. 관리자 비밀번호나 Secret 키를 프런트엔드에 추가할 필요는 없습니다.

| 테이블 | 역할 | 사용자 권한 |
| --- | --- | --- |
| disposal_items | 품목명·별칭, 재질, 세부 종류, 확인 안내 | 활성 품목만 누구나 조회, 수정은 관리자만 |
| disposal_records | 회원별 입력 JSON, 부속품, 판별 결과 JSON, 시각, 규칙 버전·통계 유형 | 본인 기록만 조회·추가·삭제 |
| disposal_legacy_names | 결과가 없는 이전 이름 기록 | 본인 데이터만 조회·추가·삭제 |
| disposal_import_receipts | 이전 완료 기록의 식별자 | 본인 데이터만 조회·추가, 앱에서 삭제 불가 |
| disposal_favorites | 이름·조건을 보관하는 즐겨찾기 | 본인만 조회·추가·수정·삭제 |
| disposal_feedback | 오류 제보·미등록 품목 제안과 당시 입력/결과 | 본인만 조회·접수 상태로 추가, 검토·반영 상태 변경은 관리자만 |

이미 기존 4개 테이블을 설치했다면 `supabase/improvements.sql`만 추가 실행합니다. 기존 결과나 생성된 category 컬럼을 덮어쓰지 않고 음식물류 통계 함수를 확장하며 품목 4개 묶음을 추가합니다. `schema.sql`은 기본 테이블 원본이며 전체 새 설치에는 생성된 `setup.sql`을 사용하세요.

기존 운영 환경에서 제보 상태 ‘안내에 반영됨’을 사용하려면 `supabase/improvements.sql`을 다시 실행합니다. 이름 분류의 공용 저장소를 사용하는 경우 `supabase/ai-shared-guesses.sql`도 다시 실행해 종류 제안 열을 추가합니다.

SQL은 한 트랜잭션으로 실행됩니다. 다시 실행해도 회원·기록을 삭제하지 않고 이미 있는 품목의 관리자 수정도 덮어쓰지 않습니다. 품목을 추가하거나 수정하려면 Table Editor에서 `aliases`, `material`, `item_type`, `note`, `active`를 관리합니다. 재질과 세부 종류는 앱의 `src/domain/disposal/rules.js`가 지원하는 값이어야 합니다. 품목 로드 실패 시 마지막으로 확인한 안전한 품목 사전을 사용하고 화면에 안내합니다.

## 제보 검토

1. 관리자는 `disposal_feedback`에서 해당 요청의 품목, 당시 지역과 결과를 확인하고 검토한 요청을 `reviewed`로 바꿉니다.
2. 공식 근거로 확인한 이름·별칭은 `disposal_items`에 추가하거나 기존 품목에 연결합니다. 같은 이름으로 서로 다른 재질이 등록되지 않게 하고, 지역별 배출 기준을 바꾸는 경우에는 해당 규칙과 출처를 함께 수정합니다.
3. 새 기준이나 별칭이 사용자 화면에 보이는 것을 확인한 뒤 제보 상태를 `applied`로 바꿉니다. 반영할 수 없는 요청은 `rejected`로 표시합니다. 회원은 마이페이지에서 자기 요청의 상태만 볼 수 있습니다.

기존 활성 품목에 별칭만 추가하는 경우, 검토 후 관리자가 SQL Editor에서 `select public.apply_reviewed_disposal_alias('제보 UUID', '기존 품목 ID');`를 실행할 수 있습니다. 같은 이름이 다른 활성 품목에 등록되어 있으면 변경하지 않습니다. 성공하면 별칭 추가와 제보 상태 변경을 함께 저장합니다. 신규 품목 등록과 지역 규칙 수정은 위의 검토 절차를 따릅니다.

## 저장·조회 동작

- 회원: Supabase Auth 사용자 ID로 DB에 저장하고 같은 계정이면 다른 브라우저에서도 불러옵니다.
- 비회원: localStorage를 유지합니다. 비회원 데이터를 임의로 로그인 계정에 옮기지 않습니다.
- 입력: 물건 이름, 재질·종류, 오염·세척·결합 답변과 부속품을 `input`에 보관합니다.
- 결과: 배출 방법·처리 과정·판단 이유·재질별 결과·규칙 버전·확인일을 당시 상태로 `result`에 보관합니다. 나중에 품목 정보가 바뀌어도 과거 결과를 새 기준으로 덮어쓰지 않습니다.
- 최근 8개·전체 기록·검색·10개씩 화면 페이지 이동은 기존 흐름을 유지합니다. 서버 조회는 여러 페이지를 읽어 기본 반환 상한 때문에 기록이 누락되지 않게 합니다.
- 통계: `get_disposal_statistics` 함수가 본인의 모든 판별 기록을 집계합니다. 검색 필터·최근 8개 제한과 관계없으며 결과 없는 이전 이름은 제외합니다. 별도 통계 테이블을 중복 갱신하지 않습니다.
- 단일 삭제·전체 삭제는 DB 함수 안에서 관련 이전 이름도 함께 처리합니다. 브라우저 저장본에서 다시 생기는 문제는 서버의 이전 완료 이력으로 방지합니다.
- 탭 간 변경 알림과 창 복귀 시 재조회, 새로고침 시 DB 재조회로 최신 기록을 표시합니다.
- 저장 실패를 성공으로 표시하거나 회원 기록을 몰래 브라우저 저장으로 대체하지 않습니다. 판별 결과는 확인할 수 있지만 저장 실패 안내가 표시됩니다.

## 기존 기록 이전

현재 로그인한 Supabase 회원 ID에 대응하는 localStorage v2 판별 기록과 v1 이름을 첫 DB 접근 시 이전합니다. 원본은 보관하고 서버 이전 이력으로 중복을 방지합니다. 공개 데모 회원·다른 회원·비회원 기록은 자동 이전하지 않습니다. 손상된 기록은 제외하고, 이전 중 서버 오류가 나면 다음 요청에서 재시도합니다.

## 검증

```sh
npm install
npm test
```

SQL 검사는 PGlite의 PostgreSQL 엔진에 Supabase의 `auth.uid()` 및 역할을 재현해 실행합니다. 스키마 재실행, 공개 품목 조회, 비회원 개인 데이터 차단, 회원 간 읽기·쓰기·삭제 차단, 통계 집계, 이전 중복·삭제 후 부활 방지, 실패 시 전체 롤백을 검증합니다. 클라이언트 검사는 1,000개 초과 조회와 계정 전환 중 응답 거절도 포함합니다.

실제 프로젝트에서도 다음을 확인합니다.

1. 회원 A로 물품을 판별하고 Table Editor에서 A의 `disposal_records`에 입력·결과가 있는지 확인.
2. A로 새로고침·다른 브라우저 로그인 후 동일 기록과 통계 확인.
3. 회원 B로 로그인해 A의 기록이 보이지 않는지 확인.
4. 개별 삭제 후 A의 통계 감소, 다시 접속해 삭제한 기록이 재등장하지 않는지 확인.
5. 비회원 상태에서 이전 브라우저 기록과 기존 판별 기능 유지 확인.

판별은 현재 상태와 등록 품목을 바탕으로 한 앱 규칙이며 배출 완료를 의미하지 않습니다.
